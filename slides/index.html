Text-guided image recognition on a small board

A camera-based scene classifier. Enter phrases such as “an opened book” and “a closed book”, then register examples in the target environment.

  • 1.40 M parameters, mostly int4, using 768 KB. Each frame requires 159 million multiply-accumulate operations (MACs)
  • ~$50 Forgix board with an RP2354A microcontroller (MCU) and Efinix Trion T8 FPGA
  • All eight convolution layers use the FPGA accelerator
  • 265 ms for the encoder. Camera frame: 282 ms from component timings, 293 ms measured end to end
  • 5.97× faster than the MCU alone at the same 320 MHz. All 512 output floats match the C reference bit for bit

The board runs image inference locally and displays the result on an RGB LED. The host handles text encoding and setup.

The MCU stores the model and sends convolution blocks to the FPGA.

Text encoding runs on the host.
Image encoding runs on the board.Both encoders produce vectors in the same embedding space. A text vector is needed only when a query changes, while an image vector is needed for every frame. This separates the large text model from the device’s continuous inference workload.

Model and hardware
How CLIP-style embeddings, model distillation and FPGA resources determine the design.
Image and text in a shared embedding space
Image and text encoders learn compatible vector representations. Their similarity provides a score for each text query.
Two encoders
An image encoder and a text encoder learn from paired images and captions.
Similarity score
Normalized vectors share an embedding space. Their dot product gives cosine similarity. This project uses 512 dimensions after projection.
Text-defined classes
Text descriptions define candidate classes without retraining the encoder. This device still uses scene registration to improve decisions.
Execution frequency
The text encoder runs when a query changes. The compact image encoder runs for every camera frame.

CLIP (OpenAI, 2021) introduced this approach. The current teacher is SigLIP 2 SO400M, which uses a sigmoid-based training loss.

Distilling a model that fits the board
A small CNN learns to approximate the large teacher model’s image embeddings. The host continues to use the teacher’s text encoder.
Training the student

The student learns the teacher’s 512-dimensional projected output for the same image. This lets its output be compared with the teacher’s text vectors.

1.40 M parameters, 159 MMAC, eight 3×3 convolution stages. Design limits: 1.5 M parameters and 250 MMAC.

Measured task retention

The original student retained 94% of queries that its teacher answered correctly. The current teacher and int4 model retain 91%.

These are retention results on the evaluation task. They are not the device’s accuracy in a new room.

Matching the embedding space

The teacher changed from CLIP ViT-B/16 to SigLIP 2 SO400M. A fixed principal component analysis (PCA) projection reduces 1152 dimensions to 512.

Two incompatible spaces can have the same dimension and still produce a numeric score. export.json identifies the space, and a weight CRC32 check detects the wrong model on the board.

FPGA resources and parallel computation
The FPGA implements a dedicated convolution accelerator. Parallel arithmetic helps only when memory and data transfer can keep it supplied.
Available resources

Logic elements (LEs) contain lookup tables and registers. Dedicated multipliers and block RAM provide arithmetic and storage resources.

A bitstream configures the circuit. In this accelerator, control logic schedules parallel operations instead of executing a CPU instruction stream.

Parallel multiply-accumulate

Convolution contains many multiply-accumulate operations. This tile performs 16 MACs per clock when operands are available.

Integer arithmetic makes exact comparison with the C reference possible. Tests check both intermediate sums and final embeddings.

Trion T8 limits

7,384 LEs, eight 18×18 multipliers, and 24 blocks of 5 kbit RAM. Total FPGA memory is 15.4 KB.

The current design uses 6,265 LEs (85%), all eight multipliers, and 21 memory blocks (88%). Both logic and memory limit further expansion.

System architecture
The host encodes text. The MCU schedules image inference. The FPGA accelerates convolution through a narrow data link.
Host, MCU and FPGA responsibilities
The FPGA accelerator, called the tile, stores one computation block at a time. The MCU holds the complete model and schedules those blocks.
Host

Runs the text encoder when a query changes and sends its 512-dimensional vector over USB. Loads the FPGA bitstream at startup.

Training, quantization and model export also run off-device.

MCU core 0

Controls transfers using PIO (programmable I/O) and DMA (direct memory access). Prepares commands and checks returned data.

PIO supplies the FPGA clock during transactions, including the cycles needed for computation.

MCU core 1

Prepares the next block’s weights and input data, then writes results to the activation buffer. Two lock-free ring buffers coordinate the cores.

In the current 270 ms benchmark, core 1 is busy for 149 ms. Most of that overlaps link activity, leaving 5 ms of waiting on core 0.

FPGA tile

Stores 2,048 running sums in int32; 16 MACs per clock. Eight multipliers are dedicated hardware and eight use logic elements.

The tile also unpacks int4 weights and requantizes outputs. The MCU supplies each block’s operands.

Design boundary: the MCU manages the model and memory layout. The FPGA accelerates block-level arithmetic. Transfer scheduling connects the two.
4-bit weights, 32-bit accumulation
int4 describes the weights. The tile holds running sums in int32.
255 × 7 = 1,785
Even one product exceeds the int4 range (−8 to 7).
A wide accumulator adds products across all 3 × 3 taps and input channels.
Typical intermediate layers return 8-bit codes after FPGA requantization. The final convolution converts to float on the MCU.
Image inference pipeline
A 128 × 128 RGB image becomes a 512-dimensional embedding. The eight convolution layers require 174 computation blocks in total.
Quantize
Normalize to [−1, 1], divide by in_scale, round and clip to ±127. Only conv0 uses signed input activations.
Eight conv stages
3 × 3 kernels, padding 1, no bias. Export folds batch normalization into the weights. 174 blocks, 1,856 passes, 6,264 transactions.
Pool and head
Average the 4 × 4 × 256 output spatially, then apply a 256-to-512 linear layer. Its 131 KMAC workload stays on the MCU.
Decide
Compare the embedding with the text vectors, normalize scores using the room background, and decide the object state and presence.
Numerical consistency: accumulation uses int32 in both the FPGA and C reference. The final convolution output becomes float before average pooling, avoiding an extra integer rounding step.
Block scheduling for limited FPGA memory

A complete convolution layer exceeds the FPGA’s memory. The MCU divides it into blocks that fit, then sends them in sequence.

  • Each block uses up to 2,048 int32 accumulators and a 2 KB input slice
  • Per frame: 174 blocks, 1,856 passes through channel/kernel groups, 6,264 transactions
  • ACT: send inputs. WGT: send weights. RUN: compute. DRAIN: read results.

All model weights reside in MCU flash. The MCU transfers only the weights needed for each block to the FPGA.

The tile can requantize outputs to one byte before DRAIN. In the M15 test, this reduced return-transfer time from 153 ms to 41 ms.

The FPGA reuses the same storage for each block.
MCU–FPGA data link
Board wiring limits the data bus to three bits toward the FPGA and one bit back to the MCU.
  • Pin-map check: six header pins reach the MCU, 13 GPIOs are unbonded, and the widest usable consecutive group is three bits
  • Return path: only GPIO6 is available. GPIO5 is CDONE, and GPIO7 has no package pad
  • Clock jumper: moving the clock to a clock-capable FPGA pin frees the third data line
  • Measured throughput: 26.4 MB/s toward the FPGA and 8.9 MB/s back

The accelerator receives weights and input activations, then returns a smaller result. This workload suits the asymmetric link.

The MCU supplies clock cycles for computation as well as transfer. Raising the link clock therefore speeds up both.

PIO and DMA handle transfers. The DMA checksum unit computes CRC during transfer. Requantizing in the FPGA reduces return traffic.
The FPGA clock comes from PIO side-set: an output pin controlled by each PIO instruction. The tile has no independent free-running clock.
Link transaction format
Each transaction carries a command, optional data and integrity checks. The diagram uses one cell per byte.
Framing

The frame begins with a5 5a, followed by a command and a 16-bit length. The receiver searches for this preamble to recover synchronization.

Seven states

The receiver handles the header, payload, execution, response and checksum in seven states. RUN has no payload and waits for computation to finish.

Checked both ways

CRC checks the payload in both directions. A status byte reports command results. Tests also compare the complete 512-float output with the C reference.

int4 weight transfer with unchanged arithmetic
1,403,744 parameters in 767,840 bytes. Seven layers use four-bit weights. The first convolution and final linear layer keep eight-bit weights, giving 54.7% of the all-int8 size.
Unpacking at the input

Each byte contains two signed four-bit weights. The tile reads the low nibble first and sign-extends each weight to eight bits before storing it in wbuf.

Weight-buffer width and multiplier inputs remain unchanged. Packing reduces transfer size without changing the stored numeric values.

Same multiplier inputs

The existing multiplier computes the same products. The same golden values verify both packed and unpacked weight transfer.

cfg_w4 selects weight width for each block at runtime. The exported model specifies each layer’s width, so one bitstream handles both formats.

Measured transfer reduction

Weight traffic falls from 2,230,272 to 1,142,784 bytes per frame. Weight-transfer cycles fall from 6.66 to 3.76 million.

Other commands are unchanged. Saving 1,087,488 bytes removes 2.90 million link clocks, consistent with eight bits per byte over three data lines.

Transfer reduction does not guarantee equal CPU savings. Core 1’s weight preparation measured 284 ms versus 290 ms. It reads fewer bytes but must unpack each weight, so its processing time changes little.
How overlap affects frame time
Reducing one operation helps the frame only when that operation delays other work. These historical experiments show the effect of overlap and waiting.
Smaller gains than predicted
  • M7d: 563 ms of CPU work remained outside the DMA transfer interval
  • M7e: moving work to core 1 saved 193 ms, versus 380 ms predicted. Some work already overlapped DMA
  • M7f: removing 157 ms from core 0 saved 59 ms overall because FIFO waiting increased
  • Three-bit link: 286 ms less transfer time initially saved no frame time. Removing other bottlenecks later recovered 165 ms
  • M10: the expected ~450 ms bottleneck measured only 32 ms, so the proposed optimization was dropped
When savings reach the frame
  • M7i: an 84 ms reduction in a queue that blocked core 0 produced 79% of that reduction in frame time
  • M16: the same 16.30 million FPGA-clock reduction produced 100% or 66% of the expected frame saving, depending on link configuration
CPU time versus waiting time
  • Waiting determines the critical path. In one profile, core 1 spent 82 ms preparing weights, but core 0 waited about 20 ms. Eliminating all 82 ms would not save 82 ms per frame.
A passing clock rate
does not establish the maximumEarly tests started at 150 MHz system / 75 MHz link and only lowered the clock after failure. That procedure never tested higher rates. Testing upward later reached 280 MHz system / 140 MHz link with bit-exact results in three boots. Measure both passing and failing rates before treating a clock setting as a limit.
Clock frequencies that fail between passing rates
The diagnostic test found two failing link-frequency bands, with passing rates on either side. Higher frequency did not always mean failure.
Observed failure bands

Failures occurred at link frequencies of 39–41 MHz and 122–130 MHz. Tests reproduced both bands across three boots.

The band centers are about 86 MHz apart. A round-trip timing model estimates a delay of 11.7 ns from that spacing.

Timing-model interpretation

Fitting each band separately gives a setup/hold window of 0.73 ns and 0.83 ns. These are estimates from the model, not direct oscilloscope measurements.

Increasing core voltage shifts the band upward by about 1 MHz per 0.05 V. This is consistent with a reduced propagation delay.

Diagnostic versus full application

The m6 diagnostic passed at 344 MHz system / 172 MHz link with 1.30 V core voltage. At 348 MHz the MCU hung.

These limits do not transfer to the full application. It uses 320 MHz at 1.25 V, and its link stops responding at 340 MHz.

An initial explanation blamed the PLL configuration. Tests that changed the PLL’s internal oscillator setting did not support it. Measure the failure band in detail before assigning a cause.

From embeddings to decisions
A correct embedding is only the input to the decision rule. The device also needs room calibration, scene references and an empty-scene decision.
Calibrating similarity scores to the room

Raw cosine similarity is not a calibrated detection score. Tests found query bias, background bias and temporal drift.

  • Query bias: a cosine of 0.27 can be high for one phrase and low for another
  • Background bias: laptop ranked first in all five test scenes, even though none contained a laptop
  • Drift: across 500 static frames, four queries fell together by about 1.5 z-score units over four minutes

Room calibration: measure each query on an empty scene, then express its score relative to that background. This reduces background bias but does not eliminate every source of drift.

// the score is not the cosine
z[i] = (cos[i] − qbg[i]) / bg_spread(i);
qbg is the mean background cosine. bg_spread is its standard deviation with a lower bound. Estimate both over the first 30 empty-scene frames, then freeze them.
BackgroundEffect
Frozen (default)Persistent objects remain different from the initial background.
Continuously updatedA stationary object gradually becomes part of the background.
Before eight background frames, the score does not use the estimated spread. A 0.001 lower bound prevents division by a near-zero value.
State classification and presence detection
The device must decide both which registered state is closest and whether an object is present. These decisions use different comparisons.
level = mean(z)       // shared score component
c[i]  = z[i] − level  // centered query scores

State: subtract the mean across queries. This removes score changes shared equally by all queries. Compare the resulting vector c[] with registered class references.

On two recorded runs, the revised state rule improved accuracy from 44.2% to 84.2% and 87.5% to 95.8%.

Presence: using level failed because it retained the common drift. The current rule instead compares distance to the closest class with distance to an empty-scene reference.

Conceptual nearest-reference regions. With two queries, the centered scores lie on a single line.

Limits of the current device:

  • Environment-specific: it distinguishes scenes registered in that room and lighting
  • One result per image: no bounding boxes or validated object counts
  • Pair-dependent accuracy: four successive tests scored 95.8 / 90.8 / 50.0 / 34.2%
  • Wording matters: “an empty glass” won on only 6.7% of frames labeled as that state in one evaluation
  • Registration statistics do not certify accuracy: eight prospective tests did not support the proposed quality thresholds

Implementation lessons
Hardware limits, build tools and measurement errors that affected the implementation.
Implementation problems and fixes
Unusable external memoryM0 · M5b
The PSRAM chip is physically present, but its ID response arrives 18 bit periods out of position. The design therefore stores all weights in the MCU’s 2 MB flash.
Automating peripheral setuprtl/
The Efinity flow used here required peripheral XML normally produced through its GUI. rtl/mk_peri.py generates that file from the interface description for automated builds.
Place-and-route variabilityM11
A seed that performed well on one netlist became the worst of four on another: 59.9 MHz versus 63.9 MHz. The repository preserves verified bitstreams as ASCII hex.
Misleading profiling countersM14 · M17
Two callbacks accumulated time in the same counter, mixing separate operations. Splitting the measurement exposed an 82 ms weight-build cost. Counter scope must match the operation being measured.
CRC format mismatchM18
The model check compared 0x… with 0X… and rejected matching weights. All four offline tests covered only mismatches. Tests must include the valid path as well.
Uncontrolled scene timingM19
Inferring scene boundaries from scores made two A/B tests disagree. A 13-frame mean was stable to ±0.05, yet visits differed by 0.85 against an effect of 0.08. Record scene timing and repeat object placement.
Lessons for similar projects
End-to-end measurement
  • Profile both computation and waiting. Compare optimized and baseline runs in the same boot, and keep clock settings explicit.
Measured clock limits
  • A passing rate confirms that setting only. Test higher and lower rates, and distinguish a diagnostic benchmark from the full application.
Failure-band characterization
  • Use a fine frequency sweep to find the edges of a failing band. Treat a physical explanation as a hypothesis until further tests support it.
Embedding compatibility
  • Equal vector dimensions do not guarantee compatible embeddings. Record the model and projection identity, and verify the weights on the device.
