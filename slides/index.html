01
What is fpga-open-vocab
You type a phrase on a laptop. A board the size of a credit card, with no GPU and no network, watches a room and tells you when it sees the thing you described.
What is fpga-open-vocab?

An image-query appliance: point it at something, type "a person smiling", and it answers.

  • Runs a distilled CLIP-style image encoder — 1.40 M int4 parameters, 159 MMAC per frame
  • On a ~$50 Forgix board: an RP2354A MCU beside an Efinix Trion T8 FPGA
  • All eight convolution layers execute in the fabric, off a live camera
  • 282 ms per camera frame — 265 ms of it the encoder — and bit-exact: 512 of 512 embedding floats identical to the plain-C reference
  • 5.97× the same model on the MCU alone — both measured in one boot, both at 320 MHz

No cloud, no GPU, no network. The answer comes out on an RGB LED, so the laptop can be unplugged once it is running.

What you see in the room: the LED sits green on an empty desk, swings toward red the moment the described thing comes into shot, and holds there — it measures presence, not change.

What you see on the console: per-frame cosines, z-scores, the winning query, and the frame time in milliseconds.

A new question can be sent to a running board with no reflash — the weights never change, only the six vectors they are compared against.

In M9's first demo, book swung from last place to first in the single frame the book came back into shot.

The board never reads your words.
It only ever sees 512 floats and an image CLIP's two towers emit into one shared space, so the language half can run anywhere — and the only half that has to be on the device is the one that runs once per frame instead of once per query. Everything in this talk is a consequence of that asymmetry.
02
The technology stack
Four things you need before the architecture makes sense: what CLIP is, what distillation buys, what an FPGA actually is — and why this particular board forces every decision that follows.
CLIP 101
Two encoders trained so that a photograph and its caption land in the same place. Everything fpga-open-vocab does is a consequence of that one property.
Two towers
An image encoder and a text encoder, trained on hundreds of millions of caption–photo pairs to agree.
One shared space
Both emit a 512-d unit vector. Similarity is one dot product — no classifier, no labels, no head to retrain.
Zero-shot
The classes are written at query time. Change the question without touching a weight — which is the whole appeal on a device.
The asymmetry
Only the image tower is in the hot loop. So only the image tower has to be shrunk down onto silicon this small.

CLIP is arXiv 2103.00020 (OpenAI, 2021). The teacher used here is SigLIP 2 SO400M — same idea, a sigmoid loss instead of a softmax over the batch, and a much stronger reading of word order.

Distillation 101 — and the trap it sets
The teacher is a transformer orders of magnitude too large for this board. The student is trained to imitate its output vector, not its labels.
Teacher → student

The student sees the same images and is trained to reproduce the teacher's 512-d output. What it inherits is the embedding space — which is exactly what the text side needs it to share.

1.40 M parameters · 159 MMAC · eight 3×3 conv stages, under a 1.5 M / 250 MMAC budget set by the board.

What it costs

M4 measured the student retaining 94% of the queries the original teacher itself gets right. After the teacher swap and int4 weights, 91%.

Quantization is nearly free: the exported int8 model scores 0.896 against fp32's 0.892 on the task — not worse, which is the only claim worth making.

The trap

The teacher changed mid-project — CLIP ViT-B/16 → SigLIP 2 SO400M, squeezed 1152-d → 512-d by a frozen PCA. Both spaces are 512-d, so pairing a query from one with a student from the other scores instead of failing. No exception. No NaN.

Guard: an export.json names the space beside the weights, and the board prints a crc32 of the weights it is actually running so a stale flash is refused before a query is sent.

FPGA 101 — and why one this small
A field-programmable gate array is a sheet of uncommitted logic you wire into a circuit. You are not writing a program; you are describing a machine.
What is in one

Logic elements (a small lookup table plus a flip-flop), a routing fabric between them, a handful of hard multipliers, and some block RAM. You compile a hardware description into a bitstream that configures all of it.

It has no instruction pointer. Everything you describe happens every clock, at once.

Why for this workload

A convolution is a wall of independent int8 multiply-accumulates. A CPU does them one or two at a time; the fabric does sixteen every clock, for as long as you can feed it.

And it is deterministic — the same 174 blocks take the same number of cycles every frame, which is what makes "bit-exact against a C reference" a testable claim.

The T8 is tiny

7,384 logic elements. Eight 18×18 multipliers. 24 blocks of 5 kbit — 15.4 KB of on-chip memory, total. A mid-range FPGA has a hundred times that.

The design uses 6,265 LE (85%), 8 of 8 multipliers, and 21 of 24 memory blocks (88%). It started at 33% of the logic and memory was the only thing running out; three milestones of arithmetic later, both are nearly full.

03
Architecture deep-dive
Three machines, one wire, and 6,264 transactions per frame — who runs what, how a convolution layer is cut into pieces small enough to fit, and where the milliseconds go.
Who runs what
Three machines and a wire. The split is forced: the model does not fit in the fabric, and the multiplies do not fit in the time budget of the MCU.
Host

Runs the teacher's text tower, once per query. Pushes 512 floats and the bitstream over USB.

It is also the only place the model is trained, quantized and exported — and it can be unplugged afterwards.

MCU core 0

Owns the wire. Stages each block, drives the link with PIO + DMA, checksums as the bytes go past, and decodes what comes back.

Also the tile's only clock — the fabric ticks when core 0 pushes a bit and not otherwise.

MCU core 1

Builds the next block's weights and input strips, and scatters results back into the activation buffer — over two lock-free rings.

509 ms of work per frame that mostly hides inside the wire's shadow. Only what does not fit shows up as stall.

FPGA tile

2,048 int32 accumulators, 16 MACs per clock — eight hard multipliers and, since M16, eight more built out of logic. Plus int4 unpacking (M14) and the requantize epilogue (M15).

It holds no model. It is a very fast, very small dot-product engine that is handed operands and asked for sums.

The one-line summary: the MCU knows what the model is; the FPGA knows how to multiply. Everything hard in this project is at the seam between them.
One frame, in order
128 × 128 × 3 in, 512 floats out — and the middle step happens 174 times.
Quantize
Normalize to [−1, 1], divide by in_scale, round, clip to ±127. conv0 is the only stage that ever sees signed input.
Eight conv stages
All 3 × 3, padding 1, no bias — batch norm folded into the weights at export, so the hardware only ever sees a plain int8 convolution. 174 blocks · 1,856 passes · 6,264 transactions.
Pool and head
4 × 4 × 256 averaged to 256 floats, requantized, then one 256 → 512 linear. 131 KMAC — small enough to stay on the MCU.
Decide
The 512-d embedding is compared against each query, standardized against this room, split into presence and state, and put on the LED. That is section 05.
Two details are load-bearing later. The accumulator is int32 and must stay int32 — it is the one value the FPGA is checked against, and C will silently widen it the moment an int64 creeps into the expression. And conv7 emits float rather than codes: its output is only 16 KB, and quantizing immediately before an average pool would wash the codes out anyway.
Cutting a layer into blocks

A conv layer is far too big for 15.4 KB of block RAM. So the MCU cuts it into pieces the tile can hold and streams them past.

  • The tile holds 2,048 int32 accumulators and a 2 KB slice of input — that is the entire working set
  • One frame becomes 174 blocks, 1,856 passes and 6,264 transactions
  • Four command types per block: ACT (push activations), WGT (push weights), RUN (compute — carries no data at all), DRAIN (read the answers back)

Weights are resident, not streamed. All 768 KB live in the MCU's flash and are pushed as the schedule needs them. The alternative — a big model in external memory — is the option that does not exist on this board.

Since M15 the tile requantizes internally and DRAIN returns one byte per accumulator instead of four, which took the return path from 153 ms to 41 ms on the board.

The tile's whole working set is one block at a time
The link: 3 bits out, 1 bit back
The plan was an 8-bit bus. The netlist said no — and the shape of everything above follows from that one measurement.
  • M0 extracted the pin map from the vendor's KiCad source. Only 6 header pins reach the MCU, 13 GPIO are unbonded, and the widest contiguous run anywhere is 3 bits
  • The return path is 1 bit and cannot be widened: GPIO5 is CDONE and GPIO7 has no pad, so GPIO6 has no neighbour
  • One soldered jumper moved the clock out of the data pins, buying the third data bit and the only clock-capable ball the MCU can reach
  • Measured: 26.4 MB/s forward (1.6% under the computed ceiling) and 8.9 MB/s back

The asymmetry is a feature. It suits an accelerator that is fed weights and activations and asked for a much smaller answer — and it is why the design pushes whole layers rather than shuttling operands.

Half of the wire time is the tile computing, not bytes moving. That is why raising the link clock bought far more than the byte rate alone predicted.

Clock1PIO side-set — the MCU is the tile's only clock
The forward path is PIO + DMA, and the DMA sniffer hashes the bytes as they go past, so the CRC costs nothing. The return path is one pin and always will be — which is why M15 moved the requantize into the fabric so DRAIN returns a byte per accumulator instead of four.
And because the clock is side-set from the MCU's PIO, the fabric only ticks while the MCU is pushing. There is no free-running tile to wait on.
One transaction on the wire
Six thousand two hundred and sixty-four of these per frame. Cells are bytes, not clocks.
Framing

A two-byte preamble a5 5a, then cmd and a 16-bit length. The receiver hunts for the preamble, so a resync costs one transaction rather than a reset.

Seven states

R_HUNT → R_HDR → R_PAY → R_EXEC → R_WAIT → R_TX → R_CHK. R_WAIT exists for RUN alone — the one command that carries no payload and takes all the time.

Checked both ways

A CRC over the payload each direction, plus a status byte. Every "bit-exact" claim in this talk is 512 of 512 floats on top of zero non-exact transactions.

Half the weight bytes, bit-exact
1,403,744 parameters in 767,840 bytes. Seven of the nine layers are nibbles, two per byte; conv0 and the head stay 8-bit, which is why the ratio is 0.547 and not 0.5. The multiplier never finds out.
Where the nibble is undone

At the write port, not at the multiplier. Two weights per byte, low nibble first, sign-extended to 8 bits on the way into wbuf.

Low-nibble-first is not a convention, it is what makes byte b land on lanes 2b and 2b+1 with no shuffle — the tile already reads wreg[4*j +: 4]. Storage stays 8 bits wide, so wreg, the fan-out and the multiplier operand are bit-for-bit what M6b built. The Logic-Level-0 path M10 measured never moved.

The product does not change

Same 10×8 DSP, same shape, identical product — so tb_gemm's golden values needed no separate arm and no wire format moved.

cfg_w4 is a runtime input per block, not a bitstream parameter — --ends8 pins conv0 to 8 bits while frame.c runs all eight convolutions on one tile, so both widths have to be live at once. Width belongs to the exported blob (d->wbits), never to the host.

What it bought

Weight payload 2,230,272 → 1,142,784 B a frame. WGT 6.66 → 3.76 Mclk; ACT, RUN and DRAIN identical to the digit, which is what says only the width moved.

121 ms of frame in configuration A, 35 in C — the narrow link is where it pays, because what it deletes is wire bytes. The 2.90 Mclk over 1,087,488 bytes is 2.667 clocks per byte, which is 8 bits over three data lines exactly. Nothing is unaccounted for.

And the non-result is the useful half. Core 1's weight builds measured 284 against 290 ms across a doubling of the weight bytes. The builder is charged per weight, not per byte — it reads half as much flash and does an unpack the 8-bit arm does not, and the two cancel. Which is the next slide, three milestones early.
A component saving is not a frame saving
Five consecutive milestones predicted a component saving correctly and then collected less than face value at the frame — by a different mechanism every time.
The pattern
  • M7d left 563 ms of CPU outside the wire it thought it had covered
  • M7e projected 380 ms from the second core and got 193 — work already hidden in a DMA window costs nothing whichever core runs it
  • M7f moved 157 ms off core 0 and bought 59, with 101 coming back as stall behind one FIFO
  • the jumper saved 286 ms of wire and 0 ms of frame, until three reasons were found and 165 recovered
  • M10 was scoped around ~450 ms and measured 32 — so it was closed without being built
The exception
  • M7i converted at 79%, and the reason proves the rule: all 84 ms came out of the one queue whose overruns become core 0's stall instead of hiding in the wire's shadow. The same 84 ms taken from the other queue would have collected far less
  • M16 converted at 100% and 66% simultaneously, same board, same run, same 16.30 Mclk in the tile. What differed is what was standing behind it — the faster link configuration runs out of shadow first
And the mirror
  • A component cost is worth face value only if something is actually waiting on it. Core 1 spends 82 ms building weights, but it is only 56% busy — core 0 waits about 20 ms, not 82. Two milestones were planned against a cost nothing was blocked on
A ladder that only steps down
cannot find a ceiling —
it can only confirm the rung it starts on Every clock sweep in this project descended from 150 MHz and stopped at the first rung that passed. So the logs said "bit-exact at 75.0 MHz" and everyone read "bit-exact up to 75.0 MHz". Two milestones' worth of plans were written around a limit that had never been measured — including one milestone's own statement that the tile "is the one line no link change can touch". Asking for more got 280 MHz sys / 140 MHz link, three boots, every cycle count identical to the digit. Worth auditing anywhere a measured pass has been quietly read as a measured bound.
The ladder is not monotonic
Filling the clock sweep in at 4 MHz found something better than a faster rate: a repeatable physical measurement, taken with a firmware constant and a stopwatch.
Two dead bands

Not one bad rung but two contiguous bands — link 39–41 and 122–130 MHz — with passing rates on both sides of each, in three boots.

They are spaced 86 MHz apart, which is a round-trip delay of τ = 11.7 ns. Their widths grow linearly with frequency, exactly as a fixed setup-and-hold window must.

Solved twice, independently

Solving each band separately for that window gives 0.73 ns and 0.83 ns — two measurements 13% apart, from data that never touched each other.

Sweeping core voltage moves the band +1 MHz per 0.05 V, upward, exactly as faster silicon and a smaller τ require. Cold versus warm shows nothing.

The ceiling, and its price

344 MHz sys / 172 MHz link is bit-exact — the Trion closing paths at 2.65× its signed-off Fmax — and 348 hangs the MCU with no link error, so it is the core, not the fabric.

Bit-exact to 344 at 1.30 V, 340 at 1.25, 332 at 1.20, 312 at 1.15. Not one non-exact transaction at any rail — every failure up there is the core going quiet. This is an m6 sweep, and it does not transfer — the appliance ships 320 MHz at 1.25 V, wedges unrecoverably at 1.15, and its link is dead at the 340 this table calls bit-exact.

The story this replaced was clean, published, and wrong. The first explanation blamed the PLL's VCO selection; forcing the same rate through a half-rate VCO fails identically, and a higher VCO passes. A hole in a coarse sweep is not a hole until the sweep is fine enough to see its edges — measure the width before explaining the cause.
05
From 512 floats to an answer
The part that took the longest and looked easiest. Thirteen milestones between a working encoder and a device that is right about what it is looking at — with two rules retired along the way.
A cosine of 0.27 means nothing

The encoder is finished and bit-exact, and the board still cannot answer a question. Three reasons, all of them measured on the bench:

  • 0.27 is large for one phrase and small for another. There is no shared scale across queries
  • This room is not the dataset. Across five bench scenes — a whiteboard, a book's two covers, a wine glass, a covered lens — the query laptop led every one of them on the raw cosine, with no laptop anywhere in shot
  • A device pointed at a desk drifts. 500 static frames: all four queries fall together by ~1.5 z over four minutes as the camera's own exposure creeps

Why the room wins: the training negatives are averaged over fields and food and dogs, while every frame this camera has ever taken is an indoor desk in front of a window. The residue is a property of the room — and the room is the only place it can be measured.

// the score is not the cosine
z[i] = (cos[i] − qbg[i]) / bg_spread(i);
Both terms are learned in this room: a running mean of each query's own cosine, plus a Welford variance for its spread, over the first 30 frames — then frozen.
Freeze?What it measures
yes (default)Presence. "Has this state appeared, and is it still there" — right for a fixed installation
noChange. Leave the same book in shot and it becomes the background — which, on an LED, looks exactly like a bug
Two guards, neither a tuning knob: under 8 frames the room's spread is not used at all, and a floor of 0.001 catches the lens cap that would otherwise send every z to infinity.
Two axes, not one
The previous design gated on a query and ranked in raw z. It scored 16.1%. The fix was to stop asking one number to answer two questions.
level = mean(z)        // is anything here at all?
c[i]  = z[i] − level   // and which one of them?

Drift lives in the common mode. Subtracting level removes it from the state decision for any query count — the way differencing two queries removes it for two. Worth 44.2 → 84.2% and 87.5 → 95.8% on the two recorded runs.

And level is exactly what the centring throws away — which is why it becomes the presence axis rather than a third enrolled class. Enrolling "absent" as a class instead scores 42.3% and 73.1%.

Frictions & learnings
The things that cost days, and the handful of rules that came out of them — which are the reason the project keeps a history file rather than deleting one.
Frictions worth the airfare
The memory that isn'tM0 · M5b
The board has a PSRAM footprint, and it is populated by accident. It answers its own ID 18 bit-times out of frame and is unusable at any rate. Every "just stream the weights from external memory" plan dies here — which is why every weight has to fit in a 2 MB stacked flash.
A GUI in the buildrtl/
Efinity generates the peripheral XML that the placer needs, and it ships that step as a GUI only — no DesignAPI.create(). So the repo carries rtl/mk_peri.py, which writes the file itself from the interface source, because a build that needs a mouse cannot run in a container.
Seeds don't travelM11
Place-and-route seeds are not portable across netlists: the seed that produced the shipped image became the worst of four on the next one — 59.9 MHz against 63.9. Every verified bitstream is therefore committed as ASCII hex, because re-running the build at the recorded settings is not guaranteed to hand back the same file.
The counter that liedM14 · M17
One profiling counter had two callbacks summing into it. Both milestones correctly measured a number that was not the number they thought, and one of them was named after the wrong function. Split, it is 82 ms against 124. Audit shared accumulators before believing a component is immovable.
A check that couldn't passM18
The weight-CRC guard compared 0x… against an upper-cased 0X…, so it refused a board that matched. Fail-closed, so nothing wrong shipped — but a check that cannot pass is not a check, and all four offline tests had exercised only the mismatch path.
The bench wasn't calibratedM19
Two A/B runs disagreed about the sign of the effect, and the board was not the reason — segment boundaries were being reverse-engineered from the score trace by eye. 13 frames pin a segment mean to ±0.05, while two runs an hour apart disagreed by 0.85 on an effect of 0.08. The variance was between visits, not inside them.
The transferable part
Measure the whole, not the part
  • A component saving is worth face value only until it uncovers the next thing — and a component cost only if something is actually waiting on it. Nothing here is claimed until it is measured in the same boot as its control
A pass is not a bound
  • "Bit-exact at 75 MHz" was read as "bit-exact up to 75 MHz" for three milestones. A ladder that only steps down can only confirm the rung it starts on — the single largest speed-up in the project was sitting there the whole time
Measure the width before explaining the cause
  • A clean, falsifiable, published explanation of the dead band was refuted by the next sweep. A hole in a coarse sweep is not a hole until the sweep is fine enough to see its edges — and the finer sweep turned a bug report into τ = 11.7 ns
When two things share a shape, guard the pairing
  • Two different 512-d embedding spaces cannot be told apart by a type system. A wrong pairing scores instead of failing — so the space is named in the export and the board prints a crc32 of the weights it is actually running

Wrap-up & Q&A
Takeaways, where to find everything — and your questions.
Takeaways
  1. 01CLIP's two towers are separable — only the image half has to be on the device
  2. 02A 1.40 M-parameter student fits in $50 of silicon and keeps 91% of the teacher's queries
  3. 03On an FPGA this small, memory runs out before logic does — 21 of 24 blocks, 33% of the LEs
  4. 04Measure the frame, not the component — and re-measure the baseline in the same boot
  5. 05A measured pass is not a measured bound. The biggest win had no design work in it
  6. 06Getting the embedding right was the easy half; turning it into a verdict took thirteen milestones
